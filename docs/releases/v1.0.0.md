# GOAD_NOMAD v1.0.0 — Segmented Foundation

**Release date:** 2026-09-01

GOAD_NOMAD v1.0.0 is the first official release of the project and establishes the segmented VMware foundation used by future milestones.

The original GOAD Active Directory scenario is preserved, but its VMware networking and lifecycle are no longer flat. The GOAD lab now deploys with explicit security zones, a lightweight routing plane, deterministic provisioning/exercise modes, persistent NAT isolation, bounded lifecycle operations, and validation that fails closed when the management plane is incomplete.

## Highlights

### Segmented VMware topology

- **NORTH** — `vmnet10`, `10.4.10.0/24`
- **SEVENKINGDOMS** — `vmnet20`, `10.4.20.0/24`
- **ESSOS** — `vmnet30`, `10.4.30.0/24`
- **MANAGEMENT** — `vmnet99`, `10.4.99.0/24`
- **GOAD-ROUTER** — Debian routing plane connected to all four zones

The stock flat GOAD VMware network is replaced by a segmented `10.4.0.0/16` architecture.

## Provisioning and exercise modes

### Provisioning mode

Used only while building or maintaining the lab:

- Windows Vagrant NAT adapters are persistently enabled and connected.
- Temporary host routes provide controlled access to protected networks.
- The router uses a permissive provisioning policy so Ansible and Vagrant can complete configuration.

### Exercise mode

The normal post-install state:

- Windows Vagrant NAT adapters are persistently disabled and disconnected.
- Temporary protected-zone host routes are removed.
- `GOAD-ROUTER` applies a deny-by-default forwarding policy.
- Only scenario-required cross-zone relationships are permitted.

## Lifecycle integration

`./goad.sh` now owns the segmented lifecycle instead of requiring operators to manually repair VMware state.

Key improvements include:

- router-first provisioning bootstrap;
- validated management readiness before Ansible starts;
- bounded VMware/Vagrant startup and shutdown behavior;
- VMware Tools/IP-discovery recovery on older Windows guests;
- recorded runtime-mode restoration;
- persistent exercise isolation across stop/start and power cycles;
- human-readable install timing and phase reporting.

## Important fixes

### WinRM reachability during VMware bring-up

Vagrant can select a protected-zone address such as an ESSOS or SEVENKINGDOMS IP as the WinRM endpoint. GOAD_NOMAD now creates the routing plane before Windows bring-up so those endpoints are reachable when selected.

### Fail-closed provisioning

An incomplete provider bring-up no longer falls through into Ansible using stale or partially valid state. All expected Windows management endpoints must be healthy before provisioning continues.

### VMware Tools recovery

Older Windows boxes can expose forwarded WinRM while VMware Tools or guest-IP reporting are unhealthy. GOAD_NOMAD adds bounded recovery, Tools verification, and retry logic instead of abandoning the whole install.

### SSMS provisioning hang

The floating SSMS installer URL began resolving to a newer release incompatible with the original GOAD provisioning flow. v1.0.0 pins a GOAD-compatible SSMS 18 installer path and keeps the install bounded.

### Child-domain DNS and ADWS readiness

Fresh-install validation exposed DNS/ADWS timing and repeat-run issues on the child domain controller. The provisioning path now explicitly hardens and validates these services so repeated runs are deterministic.

### Shutdown behavior

Graceful Windows shutdown can stall indefinitely in Vagrant. GOAD_NOMAD now applies an outer timeout, checks actual VMware power state, and force-stops only guests that remain running.

## Exercise-mode communication model

The v1.0.0 exercise firewall keeps only the validated relationships required by the existing GOAD scenario, including:

- WINTERFELL ↔ KINGSLANDING domain-controller communication;
- KINGSLANDING ↔ MEEREEN domain-controller communication;
- WINTERFELL ↔ MEEREEN DNS;
- CASTELBLACK ↔ BRAAVOS SQL on TCP/1433;
- established/related traffic.

All other routed forwarding is denied by default.

## Upgrade / operator notes

Existing GOAD_NOMAD instances created before v1.0.0 may contain an older rendered Vagrantfile. The VMware provider includes compatibility synchronization for the segmented multi-NIC settings before guest bring-up.

For a new deployment, use the normal GOAD_NOMAD workflow through `./goad.sh`; segmented networking is the default VMware path for the GOAD lab.

## What comes next

v1.0.0 intentionally freezes the network/lifecycle foundation. Milestone 2 builds on this release by introducing a first-class NORTH workstation and controlled, resettable local privilege-escalation training scenarios without changing the validated v1.0.0 segmentation contract.
